# Phase 4-1：音乐设置与媒体契约

## 需求

用户在 `config/user-config.json` 选择音乐模块后，启动本地服务并上传 MIDI，服务必须使用所选的渲染器、播放器适配器和媒体编码器。生成结果要能在任务查询和曲库接口中预览，并且媒体的实际格式、文件后缀和 HTTP 响应类型一致。

用户配置的时区也必须同时用于信件和 MIDI 任务的自然日统计。服务重启后，已经生成的任务和媒体仍应可以查询和读取。

本轮不处理原生 WebPlayer 无法接管本地曲目的问题，不修改游戏专有文件，也不新增 GUI。

## 设计

- `loadUserConfig()` 在默认模块设置上合并 `music`、`media` 和 `threeD` 选择；用户配置存在时，这些选择与信件选择一起成为启动时的运行设置。
- 启动器把用户时区传给 `MidiJobService`，并把 FFmpeg 路径作为编码器选项传入。
- 编码器声明自己的媒体扩展名和 MIME 类型。MP4 编码器生成 `.mp4` 与 `video/mp4`；未选择编码器时保留 WAV 字节并使用 `.wav` 与 `audio/wav`。
- 网关按每个已完成任务保存的媒体类型提供 GET、HEAD 和 Range 响应；持久化任务恢复时使用当前服务地址和该任务的实际文件后缀生成媒体 URL。更换编码器不会重新标记已有文件。

## 验收标准

1. 用户配置中的音乐模块选择能在本地启动装配中被实际解析，并可被测试替换实现观察到。
2. 用户时区被 MIDI 服务采用，自然日统计在非默认时区边界下正确。
3. WAV 和 MP4 两种任务的文件后缀、媒体字节和响应 `Content-Type` 相互一致。
4. 任务列表、单任务查询、曲库查询、媒体 GET/HEAD/Range 及服务重启读取全部通过回归测试。
5. `pnpm test` 和 `git diff --check` 通过；不涉及 Steam 实机验收。

## 本增量：任务生命周期与输入恢复

状态：已完成。自动化测试及 Steam 0.0.9.627 上传、生成、播放流程已通过。

### 需求

此前 `MidiJobService.generate()` 在一次同步调用中完成解析、渲染和媒体保存，上传 MIDI 只保存在进程内存。本增量已将它改为可轮询、可恢复的任务流程。

本增量只解决 MIDI 媒体任务的可恢复生命周期，不处理 `LINLI-PLAY-001`，不修改 Steam 游戏目录，不接入视频回信或 Phase 5/6 的技术路线。

### 设计

- 生成接口先创建并持久化 `queued` 任务，再由本地任务处理器推进到 `processing`、`finished`、`failed` 或 `canceled`；原版数字状态继续只在网关边界转换。
- 上传的 MIDI 输入保存到数据目录下的受保护文件，并在 SQLite 中记录输入路径、哈希、大小和文件名；服务重启后可以根据任务记录重新读取输入。
- 处理器保存 renderer、尝试次数、进度、错误码和时间戳；成功时在现有 `info_json` 中记录实际使用的 encoder 和媒体扩展名/MIME。媒体文件采用临时文件写入再发布，失败或取消不得留下可见半成品。当前代码尚未独立探测第三方 Renderer/Encoder 输出是否合法，不能把临时文件发布等同于完整格式校验。
- 取消采用协作式语义：尚未开始渲染的任务立即取消；正在运行的 Renderer 如果支持 `AbortSignal` 则停止，否则标记取消并阻止其产物发布。不能声称所有同步第三方 Renderer 都能被强行终止。
- 服务启动时恢复未完成任务：有完整输入的 `queued/processing` 任务回到 `queued`；输入缺失或校验失败的任务进入 `failed`，并保留可读错误和审计信息。
- 继续复用现有 `RenderJob`、`SqliteStore`、`AudioRenderer`、Encoder 和网关，不另造第二套媒体任务状态机。

### 验收标准

1. `/toy/midi/generate` 返回可轮询的非终态任务，随后 `/toy/midi/getGenerateResult` 能观察到 `queued/processing` 到终态的完整转换；原版数字状态保持兼容。
2. 服务重启后，未完成任务能够从持久化输入恢复；已完成任务仍能读取原媒体，损坏或缺失输入会进入明确的失败状态。
3. 取消尚未开始的任务不会启动 Renderer；支持 `AbortSignal` 的慢 Renderer 能在取消后停止且不发布媒体。
4. 同一任务最多发布一个媒体产物；失败、取消和重启恢复不会留下半成品或错误曲目记录。
5. 任务列表、单任务、批量查询、曲库分页、媒体 GET/HEAD/Range 和 WAV/MP4 MIME 契约继续通过回归测试。
6. `pnpm test` 和 `git diff --check` 通过；本生命周期增量的自动化证据不单独证明 Steam 原生接管，后续修复与实机验收已由 Phase 4-3/4-4 完成。

### 实现与自动化验收记录

- `/toy/midi/generate` 返回创建时的 `queued` 快照，后台处理随后持久化 `processing` 和终态；客户端后续查询可能直接看到终态，但生成响应本身必须为数字状态 `1`。
- 上传输入写入 `midi-media/inputs`，SQLite 的 `midi_jobs` 记录输入路径、SHA-256、大小和文件名；服务重新创建时会恢复可读输入，缺失输入明确进入失败。
- 媒体先写入带随机后缀的临时文件，再通过重命名发布；取消或失败不会发布半成品。支持 `AbortSignal` 的 Renderer 可响应取消，不支持强制终止的同步 Renderer 只保证不发布结果。
- 生命周期首轮回归覆盖排队/取消不发布，以及重启时缺失输入失败；当时完整 `pnpm test` 为 130/130 通过，后续歌单和试听回归见 [Phase 4-2](./phase4-2-library-playlist-and-module-entry.md)。
