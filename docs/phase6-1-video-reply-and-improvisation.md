# Phase 6-1：视频回信与即兴创作设计和验收

## 目标

本里程碑为“视频回信（含即兴创作）”建立独立的需求、接口和验收边界。它属于 Phase 6，必须建立在 Phase 5 的定制演奏与 3D 表现技术底座完成之后；它不属于 Phase 3-9，也不把“已有视频导入”误当成“视频生成”。

项目中的三种体验必须分开：

1. **文字回信**：信件正文、模型/Persona/Harness、有限记忆和文字状态。
2. **视频回信（含即兴创作）**：林离根据回信上下文，以视频形式回复，可能包含自拍、说话、弹琴、唱歌或根据用户话题改编演奏。
3. **定制演奏**：用户主动上传 MIDI 或选择曲目，生成自己的演奏媒体并进入曲库、播放和后续 3D 演奏链路。

视频回信与定制演奏可以共用任务和媒体基础设施，但输入、触发方式、生成器、用户入口和验收不能混用。

## 已知事实与实现判断

公开功能介绍和用户样例显示，视频回信不是普通的 MP4 文件管理功能；它是信件体验的一种可能回复形式。定制演奏则是由用户曲目或 MIDI 驱动的另一条音乐体验。公开资料没有说明原服务内部究竟采用实时渲染、预渲染还是视频模型，因此本项目不提前假定唯一的后端实现。

本里程碑采用两层方案：

- **统一生成契约**：通过独立的 `VideoGenerator` 接口和注册表接入不同实现。
- **本地技术 fallback**：先生成简单、确定、格式正确的视频，用于验证任务、媒体和网关链路；它不代表已经达到林离角色、环境、表情、动作和即兴表演的正式质量。

## 领域边界

### 视频回信

视频回信由信件上下文触发，输入至少包括信件、文字回信结果、玩家信息、角色/场景选择和可选的即兴演奏意图。生成结果是附属于该封信的视频资产及其元数据。

用户入口应围绕“收到一封包含视频的回信”设计，而不是先把它做成一个脱离信件的通用视频管理器。已有视频的导入、替换、播放和删除仍由当前 `VideoReplyService` 与 `media.videoImporter` 负责；自动生成必须走另一条服务和接口。

### 定制演奏

定制演奏从 MIDI、曲目或用户选择开始，使用音乐 Renderer、编码器、曲库和播放适配器。它可以使用统一的 `RenderJob` 生命周期，但不能把其输出称为视频回信。

## 技术设计

### 生成器接口

未来增加独立的 `VideoGenerator` 和 `VideoGeneratorRegistry`：

- 生成器有稳定的 ID、版本、能力描述和配置校验。
- 生成器接收统一的视频回信上下文，返回视频媒体和可审计元数据。
- 本地 fallback、外部视频模型和本地高质量渲染器都通过同一接口接入。
- `VideoImportAdapter` 只检查已有媒体，不实现 `generate`，不能注册到生成器注册表。

### 任务生命周期

视频回信和定制演奏共用任务基础设施的总体思想：

`queued → validating → rendering → produced → published`

并支持 `retry_wait`、`failed`、`cancelled`、`archived`，以及重启后的未完成任务恢复。两条能力线各自保存领域输入、来源信件或曲目、生成器/渲染器版本和媒体元数据。

文字回信继续使用现有的 `pending/processing/replied/failed`，不强行改成 RenderJob 状态。

### 配置边界

当前不向 `user-config.json` 增加猜测性的 `media.videoGenerator` 字段。正式配置必须区分：

- 已有视频导入检查器；
- 视频回信生成器；
- 定制演奏的音乐 Renderer、编码器和播放适配器。

配置字段、允许取值和 fallback 选择将在接口实现确定后再写入模板与 [`user-config.md`](./user-config.md)。

## 后续实现顺序

1. 定义 `VideoGenerator` 接口、注册表、能力描述和错误模型。
2. 实现本地确定性 fallback，并让它产生可被现有 FFprobe 检查器验证的技术 MP4。
3. 建立视频回信任务记录、媒体保存、查询、取消和重启恢复。
4. 增加与信件上下文关联的生成入口；不把它做成脱离信件的泛化“开始生成视频”按钮。
5. 在配置模型稳定后增加专用配置项和用户向导说明。
6. 再接入外部或本地高质量视频生成/渲染 provider。

## 验收标准

### 设计验收

- 文档明确区分文字回信、视频回信（含即兴创作）和定制演奏。
- 路线图不再出现 `Phase 3-9` 视频回信生成项。
- `videoImporter` 和 `VideoGenerator` 的职责、配置和注册表彼此独立。
- 未实现的配置字段不会出现在用户模板中。

### 代码验收

- 生成器注册表可以列出、选择和拒绝未知实现。
- fake 生成器可以验证统一输入输出契约。
- 本地 fallback 可以生成有效 MP4，并通过已有视频格式检查器。
- 任务覆盖排队、处理中、成功、失败、取消、重启恢复、媒体保存、格式检查和查询。
- 生成失败不会留下未发布的活动媒体或泄露模型密钥。

### 用户验收

- 离线本地 fallback 能让开发者完成一次从信件上下文到视频资产的完整链路。
- fallback 只作为技术链路验收，不宣称达到正式角色视频质量。
- 外部/高质量 provider 接入后，再单独进行角色表现、环境、声音、动作和即兴内容验收。
- Steam 实机验收必须由用户在目标客户端中实际观察和记录，不能用 HTTP 测试代替。

## 非目标

- 不在本里程碑实现定制演奏的 MIDI 上传和曲库流程；Phase 4 只完成基础音乐体验，定制演奏与 3D 表现技术底座属于 Phase 5。
- 不把已有 MP4 导入流程改造成生成流程。
- 不预先决定使用固定模板、实时 3D 渲染或某一个视频模型。
- 不把简单 fallback 的画面质量当作林离正式视频回信的完成标准。
