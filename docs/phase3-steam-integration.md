# Phase 3-7：Steam 游戏界面实机验收

## 目的

Phase 3 的领域服务、模型选择、后台 Worker、有限记忆、文字回信和视频回信资产已经有自动化验收。这个小里程碑验证最后一段用户路径：普通玩家启动本地服务后，在 Steam 游戏界面发送信件，并在游戏内看到文字回信。

这不是新的信件功能，也不改变 Phase 4 的音乐边界。它只是把已经完成的模块接到开发版游戏客户端，并取得真实点击结果。

## 开发版启动

在仓库根目录执行：

```powershell
node scripts/start-local-service.mjs
```

默认服务地址为 `http://localhost:27149`。默认设置使用离线 fallback，因此不需要 API Key 就能验证发送、排队和本地回复链路。若要测试外部或本地模型，先按 [模块设置与实现选择](./module-settings.md) 选择 provider，再通过环境变量传递凭据；设置文件不会保存密钥。

服务启动后应先检查：

```powershell
Invoke-RestMethod http://localhost:27149/health
```

返回 `ok: true` 只能证明本地服务已启动，不能证明 Steam 客户端已经连接。

## 受保护的游戏接入流程

1. 完全退出 Steam 游戏。
2. 对游戏目录执行只读计划，确认客户端为 `0.0.9.627`、状态为 `pristine`，并且 `canApply: true`。
3. 使用游戏目录外的备份目录；只有确认计划可应用后，才使用带 `--apply --confirm=Linli-Nocturne` 的受保护执行命令。
4. 启动 Steam 游戏，打开信件入口，发送一封测试信。
5. 观察信件是否先显示等待/处理中，随后显示文字回信；再打开详情页确认内容和状态。

安装器的只读计划和写入命令见 README。不要通过反复改写真实游戏目录来试错；如果计划拒绝执行，应先修复版本、基线或备份问题。

## 验收记录

自动化测试覆盖服务启动、健康检查、网关和 Worker，但不能替代玩家在 Steam 界面中的观察。只有用户明确报告实际完成了哪些点击、看到了什么状态和回信内容后，才能把本项从 `[ ]` 改成 `[x]`，并把结果写入交接文档。

本项通过后，Phase 3 才算完成“代码链路 + Steam 用户路径”两层收尾；之后进入 Phase 4。`LINLI-PLAY-001` 仍是 Phase 4 的原生 WebPlayer 跨层问题，不应在本项中猜测式修改。
