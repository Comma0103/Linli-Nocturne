# Phase 3-7：Steam 游戏界面实机验收

## 目的

Phase 3 的领域服务、模型选择、后台 Worker、有限记忆、文字回信和视频回信资产已经有自动化验收。这个小里程碑验证最后一段用户路径：普通玩家启动本地服务后，在 Steam 游戏界面发送信件，并在游戏内看到文字回信。

这不是新的信件功能，也不改变 Phase 4 的音乐边界。它只是把已经完成的模块接到开发版游戏客户端，并取得真实点击结果。

## 开发版启动

在仓库根目录执行：

```powershell
node scripts/start-local-service.mjs
```

默认服务地址为 `http://localhost:27149`。默认设置使用离线 fallback，因此不需要 API Key 就能验证发送、排队和本地回复链路。启用 bypass 时，服务会同时跳过发送限制、处理延迟，并向游戏兼容接口报告仍可写信，避免原版前端把写信按钮置灰。若要测试外部或本地模型，先按 [模块设置与实现选择](./module-settings.md) 选择 provider，再通过环境变量传递凭据；设置文件不会保存密钥。

服务启动后应先检查：

```powershell
Invoke-RestMethod http://localhost:27149/health
```

返回 `ok: true` 只能证明本地服务已启动，不能证明 Steam 客户端已经连接。

## 受保护的游戏接入流程

1. 完全退出 Steam 游戏。
2. 对游戏目录执行只读计划，确认客户端为 `0.0.9.627`、状态为 `pristine`，并且 `canApply: true`。
3. 使用游戏目录外的备份目录；只有确认计划可应用后，才使用带 `--apply --confirm=Linli-Nocturne` 的受保护执行命令。
4. 启动 Steam 游戏，打开信件入口，发送一封测试信。
5. 观察信件是否先显示等待/处理中，随后显示文字回信；再打开详情页确认内容和状态。

安装器的只读计划和写入命令见 README。不要通过反复改写真实游戏目录来试错；如果计划拒绝执行，应先修复版本、基线或备份问题。

## 验收记录

### 2026-09-07：已生成回信仍显示“林离回信中”

用户截图确认发送后看不到回信正文。SQLite 中两封信已为 `replied`，游戏日志也记录了详情请求，但这些证据不代表正文已显示；`read_at` 只表示详情接口被读取。

只读检查 0.0.9.627 前端主脚本后确认：原版以数字 `4` 判断已回复，网关此前却把领域字符串 `replied` 原样返回，导致前端无法建立回信展示对象。具体枚举记录见 [前端接口审计](./frontend-audit.md)。

修复需求与设计：在网关独立的信件兼容转换模块中映射数字状态，领域服务、SQLite 和 provider 继续使用 `pending/processing/replied/failed`。本次只修改仓库和重启本地服务，已有信件无需重新生成，不写入游戏目录。

验收标准：

- 列表和详情把领域状态映射为 `pending → 1`、`processing → 3`、`replied → 4`、`failed → 5`；本地接受的信件使用 `auditStatus: 2`，生成失败不伪装成审核拒绝。
- 已回复文字信件同时返回数字 `replyType: 1` 和非空 `replyText`，满足原版回信显示条件；等待和处理中不暴露回信正文。
- 测试覆盖等待、处理中、已回复、最终失败和已读行为；数据库及开发接口仍保留字符串状态。
- 服务重启后读取已有两封信，验证兼容响应；用户在游戏中重新打开现有信件后明确确认能看到正文，才记录 Steam 文字显示通过。

当前实机结论：用户已重新打开 test 和 test2，确认两封信都显示了文字回信正文；Phase 3-7 通过。客户端版本为 0.0.9.627，本次没有修改游戏目录。

自动化测试覆盖服务启动、健康检查、网关和 Worker，不能替代玩家在 Steam 界面中的观察。本次用户报告并提供截图确认：在信箱中打开 test 和 test2 后，页面上显示了林离生成的文字回信正文，完成了本项实机验收。

验收日期：2026-09-07（Asia/Shanghai）。验收结果：通过。
