# Phase 3 实验：Persona 与 Harness 融合

> 状态：离线、在线回信已有用户 Steam 截图及执行证据；称呼、落款、持续记忆和迁移已完成复验。本文记录最初在 `exp/phase3-persona-harness-fusion`（起点 `ab3baa0`）上的需求、设计、取舍和验收，成果已随 `phase3-letter-fusion-v1.0.0` 合入 `main`，不替代项目交接。
>
> 用户要求：修复未接入的离线人格、完整书信素材、落款和运行留痕；对重复或冲突能力逐项择优，建立 Linli Nocturne 自己的可插拔流程。实验仅在此分支进行，不合入或推送 main。

## 1. 范围与目标

玩家选择离线、外部 API 或本地模型后，都能获得明确的人格、书信规则、历史上下文和落款行为；启用 Harness 时，应实际使用所选模型和素材，并能查明每封信走过哪些步骤。

本轮补齐信件链路，不处理 MIDI、原生 WebPlayer、视频生成、3D 或最终安装器。保留当前成功的 Steam 文字显示契约、额度/bypass、Worker、有限重试和失败重寄。

实验开始前的缺口（下文记录原始需求，实施状态见 §4.1、§5.2）：

- FilePersonaProvider 默认只读取 olivia_lin.md，没有组装 letter_craft.md、memories.md 和示例信。
- Harness 适配器把 Persona 拼进用户来信，v18 生成器仍使用自己的人设文件，规则来源和用户输入未分开。
- LetterService 把 Persona 和历史共用一个 4000 字符上限，并静默吞掉 Persona 读取错误；增加素材后容易产生无提示截断或未加载。
- offline-fallback 是固定文本，未调用内置 local_engine.py；现有规则没有保证落款。
- 项目记忆与 Harness 档案/缓存缺少统一来源和提交边界。run-live 当前也没有把成功往来写回正式档案，不能把脚本文件存在视为跨信记忆已接通。
- letters 表只保存正文与处理状态，生成结果中的 provider/metadata 被丢弃；没有逐次尝试的实际执行记录。

## 2. 逐功能复用与取舍

| 能力 | 本轮选择 | 原因与边界 |
| --- | --- | --- |
| 人格、书信技艺、公开背景和样例 | 以 olivia-lin 的四份素材组装可选择 PersonaBundle；OliviaSoul 中互补的人设事实经逐项对照加入对应来源条目 | 完整素材可审查、可替换；示例和重构日常只作风格/角色背景，不能伪装成玩家过去经历 |
| 无模型回信 | 通过薄适配器直接调用 olivia-lin 的 local_engine.py，保留独立实现 ID | 它已有场景判断、时间/天气意象、具体回应和落款；避免另造一套固定句库 |
| 起首、场景回应、书信结构 | 优先复用 olivia-lin 的场景策略和具体细节要求；根据来信内容选择适用段落 | 不强行给每封短信凑齐所有段落 |
| 篇幅与收尾提问 | 在线生成优先采用 OliviaSoul 的按信息量伸缩和避免重复追问规则；离线引擎保留其场景化生成能力，使用统一配置说明差异 | 不同时注入常规 250–450 字与通常不超过 200 字两条矛盾硬要求；告别/重情绪单独评测 |
| 固定签名 | 内置林离书信 profile 要求首行使用配置的玩家称呼、末尾恰好一次“—— 林离” | 收尾正文可以变化，签名仍固定，两者可以共存；通过可替换输出策略实现，不写死在 LetterService |
| 预检、草稿检查与有限重写 | 复用 OliviaSoul v18 的阶段脚本/规则，通过项目适配器提供模型、PersonaBundle、有效规则和统一上下文 | 不把整套上游默认 Persona、隐藏目录查找和双份历史原样带进来；保留其它 Harness 可选 |
| 关系与事实判断 | 优先复用 OliviaSoul 的“来信人声称与已成立事实分开、关系更新需证据”约束 | 同时保留 olivia-lin 不编造共同记忆、不替用户作决定等非冲突要求；重复规则只出现一次 |
| 动态记忆 | 已实现 SQLite 近期上下文与主题画像；持续摘要/关系账本的新方案见 §4.1，计划接通 OliviaSoul 的对应能力 | 单一事实源不妨碍长期记忆；复用算法，适配存储与成功提交，不另外造一套记忆引擎 |
| 历史检索、摘要和维护脚本 | 对现有两套算法逐项登记为复用、经适配复用、被替代或独立工具；仅装配本轮需要的能力 | 备用启动器、手工刷新脚本不需要每封信都执行；不以“文件都执行一遍”作为复用成功 |
| 验收素材 | 复用 olivia-lin 的场景用例，加上 OliviaSoul 关系/事实/重复表达场景 | 上游用例中与最终规则冲突的篇幅、固定提问条款单独修订并注明原因 |

不存在“整个 olivia-lin 永远优先”或“整个 OliviaSoul 永远优先”的规则。实施前把上表落实为逐文件、逐规则的来源清单，记录实际生效位置、替代原因及对应测试；遇到确实无法独立组合的实现才限定整套 profile 的优先级。

“称呼永远是你”等上游条款与项目已有 user.displayName 需求冲突时，保留玩家配置的称呼。历史停服场景只在来信相关时启用；素材中的历史服务地区描述不能变成框架的访问限制。

## 3. 项目拥有的执行流程

```text
解析模块选择与配置
  → 组装 PersonaBundle、有效书信规则、唯一历史上下文
  → 预检
  → 所选基础模型或离线引擎生成草稿
  → 规则检查；需要时有限重写
  → 落款与输出格式校验
  → 保存正文和本次执行记录；成功往来进入唯一记忆来源
```

- 基础模型、PersonaBundle、Harness、MemoryProvider 和输出策略保持独立接口。更换模型不能改变人格选择；更换 Harness 不能偷偷换成另一个模型或读取别处的用户档案。
- 在线/本地模型复用同一输入结构。Persona 和规则进入专门的系统/规则输入，历史进入历史上下文，用户正文只作为正文；禁止再把 Persona 贴到“此前对话记忆”或当前来信里。
- 内置 bundle 记录素材 ID、来源提交、内容哈希和有效规则版本。完整读取所需文件后按章节预算组装，优先保留硬约束；不能简单 slice 把落款等后半段规则截掉。选中素材缺失、损坏或超限时明确报错或按显式策略降级，并记录原因。
- 上游 loader.py 的组装方式可直接参考复用；其依赖 skill/config.py 在当前内置快照中缺失。实施时验证依赖闭包，不未经验证调用残缺包。local_engine.py 仅用标准库，可由项目的 Python 桥接器直接载入；不移植一份平行句库。
- 新离线实现使用独立 ID（建议 `olivia-lin.offline`），当前 `offline-fallback` 保留为明确的最简降级选项。Python 未找到、超时、输出无效都产生可读错误；只有用户开启 fallback 才切换，并如实留痕。
- 离线引擎运行不发送网络请求。依赖模型推理的预检/重写阶段不得假装执行，记录为不适用或采用对应离线检查能力；配置不兼容时给出清楚诊断。
- 时间从项目 clock/timeZone 传入，不依赖运行脚本所在机器的隐含时区。weather/mood 保留为可选文风元信息，不冒充实时天气。
- 输出策略来自所选 profile。内置林离 profile 规范末尾空白和重复尾部落款，并在配置玩家名字时把称呼整理到首行；不改写用户引用中的“—— 林离”，不擅改已有历史回信。其它 Persona 可选择自己的签名、称呼规则或禁用。
- 保留现有 OliviaSoul 独立适配器作为可选旧实现；实验组合建议新增 `linli.fusion-v1` Harness ID。复用 v18 阶段脚本时新增显式输入，保留来源记录，运行产物放到单次任务隔离目录，不能逐封改写 third_party 的源码和全局规则文件。

## 4. 统一记忆来源与持续记忆增量

**已实现**：静态 Persona 背景与玩家历史分开；动态记忆由所选 MemoryProvider 提供。有限 `sqlite` 保留，新增 `olivia-soul.sqlite` 接通分层历史、持续关系账本和原文检索。关闭后不读取、不注入、不新增；成功正文、执行记录、关系账本和待整理标记在同一事务提交。

### 4.1 持续关系与长期记忆（2026-09-08）

用户批准后已实现下述增量：统一使用项目 SQLite 保存，显式提供输入，遵循身份、开关和成功提交边界。源码与自动化已完成，私有配置、真实数据库和游戏安装未改动；用户已完成新版 Steam 离线/在线验收。

**源码核对与复用选择**

| 上游能力 | 实际入口 | 本次接法 |
| --- | --- | --- |
| 最近 5 封全文、再前 5 封逐封摘要、更早五段式回忆 | `memory-lib.ps1` 的 `Build-Memory`、`Get-LetterSummary`、`Get-RollingBulkSummary` | 保留分层规则、来源区分、内容哈希及增量复用；从 SQLite 读取往来，摘要回存 SQLite |
| 结构化摘要任务 | `refresh-live-memory.ps1` 的显式输入/输出模式 | 参考其 exchanges / oldMemory 协议；适配层直接读取 memory-lib.ps1 的更完整提示词并调用所选基础 provider，避免再启动一套自带模型和缓存的任务 |
| 跨信关系账本 | `01-初始化账本.md`、`01-预检.md`，以及 `harness-4step.ps1` 的 PreviousStateTag 路径 | 保留初始化、继承与有证据才更新的过程；把上轮文件读取改为显式 previousState / relationshipMemory，结果随成功回信提交 |
| 原文检索与证据 | `history-retrieval.ps1` 的 search / read / neighbors、快照校验、查询预算；`Build-FactMemory` | 给它提供由本次有效 SQLite 历史生成的快照，保留检索和证据格式；按需检索，不为每封信强制增加一轮检索模型调用 |

核对范围是仓库已内置的 v18 文件。上游本来就按 Person 区分档案；`harness-live.ps1` 写的是临时来信档案，结束后删除，不能据此声称它提前污染了正式往来。`harness-4step.ps1` 会在生成完成前保存预检文件，如何供后续程序使用必须区分阶段产物和已确认记忆。`refresh-live-memory.ps1` 更已明确不读写正式 Markdown 或 mem_cache，不能把 APPDATA 路径当作整套算法无法复用的理由。

`refresh-live-memory.ps1` 的旧信五段式摘要提示比 `memory-lib.ps1` 简略；适配时复用后者更完整的事实归属、约定去重/兑现/撤销规则，维护一份有效版本。保留上游已有的摘要预算、按需生成和缓存复用，不额外限制来信或回信字数。固定开信、角色背景和示例继续与玩家真实往来区分；未实际交付的开信不作为共同历史。

**数据放在哪里**

- 沿用磁盘上的项目 SQLite 和现有 `letters`、`letter_attempts`；完整往来无需再复制进一张“隐藏档案表”。最近上下文的窗口变小不再等于遗忘长期事实；完整信件保留与提示词长度是两个问题。
- 已增加 memory_summaries 和 memory_states 两张表。前者保存来源 ID、内容哈希、摘要与算法版本；后者保存五段式回忆、关系账本、覆盖范围、修订号及整理/重试状态。letters.memory_allowed 标记可参与记忆的成功往来，memory_epoch 作废清空前的在途生成。没有另一套通用任务或长期 Markdown/JSON 记忆库。
- 五段式回忆继续涵盖来信人档案、未兑现约定、聊过的话题、关系和关系关键点；关系账本沿用上游的关系、依据、已承认情感、既有亲密、边界和上限。旧回忆描述历史，账本注明覆盖范围；不把两份不同年代的关系描述同时当作当前事实。
- 所有派生内容关联原始往来和处理版本，原文与较新证据优先，摘要不是独立事实。临时快照、检索索引、提示词投影可重建；调试草稿仍是诊断文件，不转成记忆。切换算法不复用无法验证兼容的旧派生状态。

**玩家与会话隔离**

- 使用已有 `user.profileId` 作为稳定玩家标识，`user.displayName` 只负责称呼。改名保留原档案；创建另一位玩家才换 ID。同名玩家也必须隔离，不能按名字猜测或合并历史。
- 同库按玩家、角色和会话标识筛选，逻辑上各有档案，无需为每个名字新建数据库文件。当前 `conversation_id` 实际承载 profileId，迁移需显式保留映射；同一林离角色切换 Persona/Harness 不等于换角色。
- 已补齐信件列表、详情、未读、已读、额度、重寄、执行记录、记忆查询及视频附件网关的 profile 过滤。同一玩家生成串行，其他玩家可独立处理。
- 使用现有配置和向导提供选择，不为本增量另造账户系统；更完整的 App 界面继续复用同一配置。

**一次回信怎样运行**

1. 从所选玩家的已成功往来、有效摘要和账本组装上下文；如需旧事细节，使用同一历史快照检索。失败草稿、其他玩家、关闭记忆期间未授权纳入的信件均不参与。
2. 保留现有预检 → 草稿 → 检查 → 必要重写/复检。预检获得真实 previousState，不再每次固定传“无”。首次接入或账本缺失时复用上游初始化入口。
3. 沿用上游语义：本次预检根据此前已发出的回信更新账本。生成中的本封来信和草稿不算已成立关系；本封成功回复带来的变化，在下一封预检吸收，不额外新增一次回信后关系判断模型调用。
4. 把最终正文、执行记录、有效预检账本及需要更新摘要的标记，在现有成功事务中一起提交。账本注明已处理到哪封历史回信，防止重复吸收；无效租约、失败尝试不能提交。若连续离线往来等造成多封尚未入账，初始化/补齐应覆盖全部遗漏往来，不能只处理最近一封。
5. 复用现有后台调度，在有信件进入下一层且缺摘要时才处理待更新标记；模型调用放在事务外。保存时校验来源哈希、修订号和处理资格，重试不重复应用，旧结果不能覆盖新状态。失败保留上次有效摘要和待处理进度，不撤销已成功回信；新信仍能看到尚未被摘要覆盖的近期成功往来。

现有 MemoryProvider 增加可选的关系状态、证据及提交材料；新实现已注册为 `olivia-soul.sqlite`，有限记忆与关闭选项保留。回信上下文只组装一次，Fusion 接收 previousState；无 Harness 的 OpenAI 兼容 provider 同样接收现有账本。新摘要使用所选基础模型，语义账本更新复用 Fusion 预检，不为无模型离线冒充一次模型判断。独立旧 olivia-soul-v18 自管记忆，配置校验禁止它与项目记忆同时开启。

**开关、离线和遗忘**

- 保持记忆默认开启；新实现落地后通过注册表、配置模板和既有向导选择，不在本方案阶段改用户当前设置，也不静默覆盖用户已明确选择的其它实现。
- 总开关同时控制历史检索、上下文、账本和摘要更新。关闭或清空时使运行中旧任务失效；保留已有信件不等于允许它继续参与回信。重新开启不能偷偷补读关闭期间的往来，历史重建须通过明确操作触发。
- “忘记这封/清空记忆”要记录排除范围并使受影响摘要/账本失效，避免仍保留的旧信或缓存再次生成被要求遗忘的内容；不因此删除用户可阅读的原信，删除原信则按明确的数据删除操作处理。
- 无模型离线模式照常保存成功往来、读取可用的已有记忆，不暗中调用外部 API；摘要和语义关系更新需要模型，不能把规则引擎说成具有同等推理能力。无可用模型时明确记录未更新，后续仅在配置允许时补处理。已有关系不能因暂时离线被清空。
- 不增加新的取悦、固定提问、时间/天气必写或硬性篇幅规则；继续保留林离的独立性和自然文风。

**落盘与换电脑**

SQLite 已持久化到硬盘，使用现有配置的数据目录即可跨进程和重启恢复。这里不需要再写重复的 save/load 脚本，不依赖退出游戏时才保存，也不持久化能够从数据库重建的缓存。

缺的是自动迁移入口：复用现有压缩/校验能力，增加一套配对导出/导入，由同一向导提供入口。导出生成一致的 SQLite 快照，并打包必要设置和快照引用的用户资产；若导出整库，就不能遗漏其中引用的媒体。路径相对包内数据根，版本和文件清单可校验；不打包密钥、游戏专有资源、运行时或可重建缓存。导入先在临时位置校验，备份现有目标再切换；新机器重定位数据目录，保留 profileId，失效的进程租约按现有规则恢复，用户不手动拼接文件。不增加云同步、定时快照服务或另一套存储系统。

**最小实施顺序与验收**

1. **接回分层记忆与关系账本**：增加必要表/字段和显式适配输入，复用上述真实脚本；已存往来不丢失，超过近期窗口仍能检索旧事实、读取关系依据。分别验证逐封摘要、滚动摘要、约定更新和账本初始化/继承，不能以“多带一段历史”代替验收。
2. **补齐提交和隔离**：复用 Worker 的调度/重试方式，覆盖成功一次提交、失败不入记忆、重复处理、断电/重启、处理过程中关闭/清空、改名与不同 profile 同名、切换 Persona/Harness。旧摘要与新原文的覆盖范围无重复或遗漏；真实关系质量仍需模型/人工观察。
3. **选择与迁移**：配置向导能选择记忆实现、切换玩家、查看/清空记忆、导出和导入；在另一目录导入并重启后，往来、摘要、账本、身份及资源引用一致。SQLite/WAL 活跃写入时的快照也需验证，不能只复制裸数据库文件冒充一致备份。

**实施与自动化结果**

- 主要落点：olivia-soul-memory.js 读取上游摘要提示词并桥接原文检索；olivia-soul-sqlite-memory.js 管理分层上下文、来源缓存和异步整理；SQLite/LetterService/Fusion 负责成功提交和账本传递。
- 头五封不调用摘要模型；第六封起生成缺失逐封摘要，第十一封起增量更新五段式回忆。错误退避 1/2 分钟，最多 3 次；后台续租，旧结果用修订号校验，下一次启用模型后可接续离线积累的任务。模型消耗由当前外部/本地配置决定，不另选隐藏 API。
- 近期原文优先分配预算，最终按时间顺序呈现；超限记录 truncated。原始信件始终保留，旧事可直接走上游 search/read/neighbors，临时快照含哈希并在结束后清理。不另加模型检索规划轮次。摘要不是独立事实，事实归属、约定去重/兑现规则直接使用上游提示词；其真实判断质量仍需人工验收。
- 首次升级只把原 memory_episodes 仍可证明的来源纳入历史，未知/已裁剪旧信不静默补读；原信件不删除。停止服务后运行 manage-user-data.mjs，可创建/切换/改名、查看状态、遗忘、重试摘要、导出/导入。设置向导可选择新记忆实现。
- 导出使用 Node SQLite backup API 获取活跃 WAL 快照，验证所引媒体完整；临时目录导入、完整性/清单校验、旧目录备份、路径重定位，失败恢复旧数据。当前 ZIP 大小上限 256 MiB，密钥和诊断草稿不迁移；自定义运行时/第三方插件需在新机器可用。导入后用户启动服务，无常驻同步或重复 save/load。
- 自动化结果（2026-09-08）：`pnpm test` **120/120 通过**，`git diff --check` 通过。新增 longterm-memory-transfer.test.mjs 的 14 项测试覆盖 5/5/旧信分层、实际摘要规则、真实 PowerShell 检索与账本、离线重启、隔离、生成/摘要途中清空、重新纳入旧信、上限退避、媒体迁移与回滚、附件网关；已有离线引擎、模型、网关回归一起通过。

## 5. 逐次尝试的执行留痕

通过可迁移的表或字段保存，成功和失败都保留有界的执行记录：

- 信件 ID、attempt ID/序号、开始结束时间、状态和错误码；
- 配置选择与实际执行分别记录：provider ID/版本、模型名、Harness ID/版本、PersonaBundle ID/版本与素材哈希、输出策略版本；
- 记忆是否开启、实际 MemoryProvider、引用的往来 ID 和上下文预算；
- 实际执行的预检/生成/检查/重写阶段、重写次数、降级原因、落款规范化结果；
- 缺失版本标为 unknown，不凭空补版本；离线实现不能留成 DeepSeek；关闭 Harness 时不得声称执行过检查脚本。

只保存必要元数据和可解释状态，不保存 API Key、认证头、完整模型请求、推理过程或不必要的正文副本。旧信件缺少来源时标明历史未知，不能倒填为本轮实验结果。

提供本地只读诊断入口或清楚的查询命令查看单封信执行过程；原版游戏的响应契约保持兼容。

### 5.1 Steam 调试增量：本机阶段诊断

2026-09-07 在线复测两次返回 `harness_quality_failed`，原记录无法说明具体被否决的项目，失败草稿也已随临时目录清理。按用户要求补充可配置诊断，不改变质量门槛：

- `letters.harness.diagnostics.enabled` 默认关闭，本次实验开启；路径相对配置文件解析，默认 `../logs/letter-diagnostics`。
- 按信件 ID、尝试序号和独立运行 ID 保存预检输出、草稿、检查结果、重写正文及复检结果；每个阶段完成立即写入，失败和中断仍可排查。
- 原始阶段输出仅存在本机诊断文件，不进入游戏接口、普通执行元数据或动态记忆；不记录请求、认证头、API 的 reasoning_content，已知密钥和临时令牌脱敏。诊断写入失败单独留痕，不使回信失败。
- 最多保留 20 份完成记录，单阶段最多 64000 字符；显式标注截断。执行接口只记录诊断 ID/状态及检查失败栏目。

### 5.2 Steam 调试增量：书信格式兜底

2026-09-07 的本机诊断显示：草稿包含玩家称呼，Harness 重写后丢失，复检仍通过。用户截图确认游戏展示与保存正文一致；这是保存前输出契约未覆盖称呼和结构，不能把模型复检通过等同于格式完全通过。

- 需求：选用林离素材包时，配置了 user.displayName 就以该称呼单独起一行；模型已经写出时间词时按框架本地时段纠正，时间/天气本身不强制补齐；已有自然收束原样保留，不自动追加邀请；落款只规范末尾签名。
- 设计：在现有 PersonaBundle.outputContract 声明 opening，沿用可替换 PersonaReplyPolicy 在保存前修复。服务只传入玩家显示名和本地时段，不绑定具体人物。自定义 Persona 未声明时不强加林离格式，none 仍可关闭。

- 取舍：篇幅基本匹配来信内容与情绪；在有效素材及实际检查输入中去掉上游 200/220 字等固定限额。保留林离有判断、有生活、温和但不讨好也不故意疏远的性格，不补具体经历或追问。时间/天气可省略；机械格式检查不代表全部语义质量通过。
- 验收：覆盖重写丢称呼、称呼中包含特殊字符、已有称呼/时间不重复、称呼后的错误时段、跨午夜、空名字、正文引用、重复执行幂等、自定义 Persona/关闭策略；通过 fake 在线 Harness 网关和真实离线引擎验证保存、记忆及执行记录一致。随后用户已在 Steam 中观察并确认新格式回信。

## 7. 验收标准

- **素材完整性**：真实 bundle 包含人格、书信技艺、公开背景和示例；可通过清单确认每份素材在生成/检查中的用途；不把评测样例答案直接塞进待测来信。
- **角色隔离**：fake endpoint 捕获的规则、历史、正文位置正确；样例内容、Persona 文本不能被记成玩家来信；人格加载失败有可见错误/降级记录。
- **模块替换**：外部 fake DeepSeek 兼容端点、本地 fake 端点、自定义 Persona/Harness、禁用 Harness 都走统一流程；验证实际调用次数和模型选择，不只断言配置解析结果。
- **真实脚本桥接**：本地 stub 端点驱动复用的阶段脚本，覆盖正常检查及一次重写；本地直接执行复用的 Python 离线引擎。mock 不替代这两个集成检查。
- **零网络离线**：离线模式不得触发外部模型；缺少 Python、超时、无效输出及启用/禁用 fallback 均有明确结果。
- **输出契约**：漏签、已有签、重复尾签、带空白及正文内引用分别测试；最终尾签恰好一次；其它 Persona 的可配置签名不被林离默认值覆盖。
- **场景质量**：复用上游的问候、日常、工作压力、音乐、情绪、感谢、告别等用例；在线风格采用本轮选定规则。机械格式检查与需要真实模型/人工判断的质量结果分别报告，不用 fake 成功冒充人格质量通过。
- **记忆**：开启、关闭、长度预算、跨午夜、连续信件、会话隔离、重启、删除后投影失效、重试去重均覆盖；关闭记忆时 Harness 不能偷偷读缓存。
- **事实约束**：不存在的共同经历、来信人单方面关系声明、重构样例等不得升级为已发生事实；来源不充分的规则归为质量验收，不能以简单关键词测试宣称全面解决。
- **留痕**：成功、失败、fallback、重写记录实际执行者和版本；正文保存与留痕失败的恢复边界有测试；旧库迁移不丢信，历史未知保持未知，错误和诊断不泄漏密钥。
- **既有回归**：pnpm test、网关冒烟、数字信件状态、bypass、Worker/重寄、Phase 4 音乐配置与媒体类型测试保持通过。
- **Steam**：代码、脚本集成与网关测试通过后，用户已使用新实验配置完成离线与在线实际回信验收；正文、落款、持续记忆和对应执行记录一致。后续修改仍需新的实机证据，不能沿用本次结果代替。
