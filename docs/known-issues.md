## LINLI-PLAY-001：本地上传曲目无法接管原生 WebPlayer

- **状态**：已修复并通过 Phase 4-4 Steam 实机验收
- **2026-09-09 进展**：只读反汇编确认原生要求 `TOD12/TOD1730/TOD20`，并要求媒体先存在于 `songStoragePath/<id>/<文件名>`；服务已修正 TOD 并自动镜像媒体，Steam 0.0.9.627 已确认本地 MIDI 可播放。
- **首次确认**：2026-09-06
- **修复前影响**：曲库中的上传 MIDI 可以上传、生成并显示，但点击“演奏”后桌面不进入演奏，也没有本地曲目声音。
- **修复前对照**：同一客户端、同一网关、同一时间，预设曲目可以正常进入演奏并产生 `webPlayerControl` 时间事件。

### 修复前复现步骤（历史记录）

1. 启动本地网关和已经接入补丁的 0.0.9.627 客户端。
2. 打开“曲库 → 我的上传”。
3. 对已生成的 `linli-performance-10s.mid` 点击一次“演奏”。
4. 等待约 5 秒。

### 历史排查与契约修正

- MIDI 文件过短：使用约 10 秒 MIDI 仍失败。
- 上传、生成和任务轮询：均成功，曲目能在“我的上传”显示。
- 回环媒体地址曾尝试 `127.0.0.1` 和 `localhost`；地址警告本身不能证明原生拒绝了媒体。
- URL 扩展名：已提供 `.mp4` URL，并保留无后缀兼容。
- HTTP 媒体协议基础能力：已实现 `HEAD`、单段 `Range 206`、`Content-Range` 和 `Accept-Ranges`。
- TOD 键值：原生实际使用 `TOD12 / TOD1730 / TOD20`，项目已改用这组值。
- `play` 桥接形状：日志确认原生收到包含完整 `song` 对象的 `cmd: "play"`。

### 关键证据

2026-09-06 14:34:00 的 `Olivia.log` 同时记录了：

- `sendWebPlayerControlCmd` 收到上传曲目的完整 `play` 对象；
- 对象中包含 `.mp4` 的 `http://localhost:27149/...` 地址和三组 TOD 条目；历史上使用的键并非后来反汇编确认的全部正确值；
- 该次观测窗口中未见新的本地媒体加载事件，具体证据强度见 [Phase 4-3](./phase4-3-native-webplayer-evidence.md)。

同期 `work/runtime/gateway-capture.log` 只有网关启动行，没有记录 `/toy/midi/media/` 请求；尚不能仅凭该文件证明所有请求均被完整捕获。预设曲目播放时则会产生正常的 `webPlayerControl` 时间事件。

### 修复方式

只读反汇编已经确认：原版 `NutStudioUI` 的 WebQuery `play` 分支会把完整 `song` 交给内部控制对象；`StudioManagerLite::playVideo` 先选择 TOD，再检查 `songStoragePath/<id>/<URL basename>` 是否存在，之后才调用 `WebPlayerClient::play`。项目已在服务侧修正 TOD，并在媒体生成成功后自动创建目录、原子写入文件；路径无法发现或没有权限时，任务结果中的 `nativePlayback` 会给出具体错误。

### 回归检查入口

若以后同类症状重现，先按已确认契约排查：

1. 查看任务 `info.nativePlayback`，检查缓存盘、发现路径和 `<歌曲 ID>/<文件名>` 是否仍存在且可读。
2. 核对 `TOD12/TOD1730/TOD20` 和完整 `song`，区分“我的上传”与歌单入口；缺少歌单元数据时先查网关，不能直接归因于 DLL。
3. 只有出现已有契约无法解释的新证据，才按 Phase 4-3 的已知调用链继续只读分析；不要重复从零调查或要求多轮盲测。

本问题已关闭，不再是 Phase 4 的开发阻塞。当前上传 MIDI 为音频 MP4 和黑屏演奏；没有 3D 人物画面属于 Phase 5 的未实现能力，不属于本缺陷复发。
